# 9. 계정별 화이트리스트 도입

## Status
제안 (2026.09.22)

## Context
필터 사전은 전역 하나이며 모든 고객의 요청이 같은 기준으로 검출된다. 그런데 허용해야 하는 표현은 서비스마다 다르다. 게임 채팅에서 일상적으로 쓰는 표현이나 특정 서비스의 상품명, 닉네임이 사전 단어와 겹칠 수 있다.

지금 고객이 예외를 둘 수 있는 경로는 단어 제외 요청(`REMOVE`) 하나다. 이 요청은 승인되면 전역 사전에서 단어가 빠지므로 다른 모든 고객의 검출 결과가 함께 바뀐다. 고객 한 곳의 사정만으로 승인하기 어렵고, 고객은 승인을 기다리는 동안 오검출을 감수해야 한다. 지금까지 접수된 제외 요청은 1건이다(2026.09.22 기준).

ADR 0008이 다루는 화이트리스트는 "`시발점` 안의 `시발`은 누구에게나 정상"이라는 전역 예외이고, 실제 적용은 후속 범위로 남아 있다. 고객 단위 예외는 그와 다른 축의 문제이며, 검출 결과에서 예외를 걸러내는 장치 자체가 아직 코드에 없다.

## Decision
계정이 화이트리스트를 용도별 그룹으로 여러 개 만들어 두고, 필터 요청에 적용할 그룹의 ID를 실어 보낼 때만 그 그룹들을 적용한다. 화면에서는 이 단위를 "허용 단어 그룹"이라고 부른다. 예를 들어 게임 서비스라면 `게임 욕설 허용 그룹`과 `친구창 욕설 허용 그룹`을 따로 두고, 전체 채팅에는 앞의 것만, 친구창에는 둘을 함께 적용한다.

- **소유와 개수**: 화이트리스트는 계정(`users`)이 소유하며 계정마다 여러 개를 둘 수 있다. 목록마다 이름을 붙인다.
- **적용 방식**: 필터 요청의 `whitelistIds`에 그룹 ID를 하나 이상 지정하면 그 그룹들의 합집합을 적용한다. 값이 없으면 지금과 똑같이 동작하므로 기존 연동에는 영향이 없다. 요청당 지정할 수 있는 그룹 수의 초기 제안은 5개다.
- **예외의 의미**: 단어를 통째로 무시한다. 검출된 표현이 목록에 있으면 검출 결과와 마스킹에서 모두 제외한다. 비교에는 필터와 같은 정규화와 대소문자 무시를 적용한다.
- **범위**: 검출에서 빼는 것만 다룬다. 계정별로 차단 용어를 더하는 기능은 고객마다 검색 구조를 따로 만들어야 하는 별개의 문제이므로 별도 ADR로 다룬다.
- **검증**: `whitelistIds` 가운데 하나라도 존재하지 않거나 요청한 API Key의 소유 계정 것이 아니면 요청 전체를 오류로 응답한다. 조용히 무시하면 고객이 예외가 적용된 줄 알고 운영하게 된다. 두 경우는 같은 코드로 응답해 남의 그룹이 존재하는지 알 수 없게 한다.

### API 계약

필터 요청에 선택 필드 하나를 더한다. `POST /api/v1/filter`의 JSON과 form 요청에 적용하고, 비동기(`callbackUrl`) 요청도 같은 필드를 받는다. form 요청은 같은 이름의 파라미터를 반복해 여러 개를 보낸다. 비동기 요청의 `whitelistIds` 검증은 접수 시점에 수행해 오류를 콜백이 아니라 즉시 돌려준다. `/api/v1/filter/advanced`는 이번 범위에서 제외한다.

```json
{
  "text": "오늘 보스 죽여버리자",
  "mode": "FILTER",
  "whitelistIds": [
    "0b6f7c1e-5a3d-4c1e-9a53-2f8f4d6f1b20",
    "7d2a9e44-1c0b-4f6a-8b1d-93c5e0a7f312"
  ]
}
```

목록 관리는 로그인 JWT를 쓰는 대시보드 API로 제공한다. 기존 `/api/v1/dashboard/keys`와 같은 규약을 따른다.

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/v1/dashboard/whitelists` | 내 허용 단어 그룹 목록 |
| POST | `/api/v1/dashboard/whitelists` | 허용 단어 그룹 생성 |
| PUT | `/api/v1/dashboard/whitelists/{whitelistId}` | 이름과 단어 목록 수정 |
| DELETE | `/api/v1/dashboard/whitelists/{whitelistId}` | 허용 단어 그룹 삭제 |

### 저장

테이블은 `whitelists` 하나만 추가한다. 식별자는 외부에 노출되므로 기존 `users`, `api_keys`와 같이 UUID를 쓴다. 단어 목록은 별도 테이블로 나누지 않고 TEXT 컬럼 하나에 담는다. `api_keys.permissions`가 같은 방식으로 목록을 저장하고 있다. 필터 경로에서 그룹마다 한 행만 읽으면 되도록 하려는 것이며, 이를 위해 상한을 둔다. 초기 제안은 계정당 10개, 그룹당 200단어다.

### 필터와 캐시

검출은 지금처럼 전역 Trie로 수행하고 그 결과에서 목록에 있는 표현을 걸러 낸다. 고객별 Trie는 만들지 않는다.

- `QUICK` 모드는 첫 검출만 돌려주므로 결과를 뒤에서 걸러 내면 안 된다. 첫 검출이 예외 표현이면 뒤에 있는 실제 비속어를 놓치게 된다. 예외가 아닌 첫 검출을 찾아야 한다.
- 필터 결과 캐시(`request_filter`)의 키는 `문장 + 모드`뿐이다. `whitelistIds`가 있는 요청에는 이 캐시를 적용하지 않는다. 적용하면 한 고객의 예외가 반영된 결과가 다른 고객에게 나간다.
- 그룹 본문은 그룹 ID를 키로 하는 짧은 TTL의 로컬 캐시에 둔다. 여러 그룹을 조합해도 그룹 단위로 캐시되므로 조합마다 따로 저장하지 않는다. 초기 제안은 사전 동기화 주기와 같은 1분이다.

## Consequences
- 고객이 전역 사전 변경을 기다리지 않고 자기 서비스의 기준을 바로 맞출 수 있다. 전역 사전은 고객 한 곳의 사정에 흔들리지 않고 보수적으로 유지할 수 있다.
- 그룹을 요청마다 골라 조합하므로 같은 서비스 안에서도 화면마다 기준을 다르게 둘 수 있고, 공통 예외를 그룹마다 중복 등록하지 않아도 된다. API Key를 재발급해도 그룹은 계정에 남는다.
- 소유 계정이 연결되지 않은 API Key로는 쓸 수 없다. 2026.09.22 기준 전체 키 37개 중 30개, 최근 90일에 실제로 쓰인 키 13개 중 8개가 여기에 해당한다. 목록을 만들려면 어차피 대시보드에 로그인해야 하고 그때 발급 이메일이 같은 키는 자동으로 연결되지만, 발급 이메일과 SSO 이메일이 다른 키는 연결되지 않는다.
- `whitelistIds`가 있는 요청은 필터 결과 캐시를 타지 않아 매번 필터를 실행한다. 요청의 88%가 20자 이하(2026.09.21 집계)라 부담은 작다.
- 목록을 고친 뒤 반영되기까지 로컬 캐시의 TTL만큼 지연이 있다. 인스턴스가 둘이라 수정 즉시 비우는 방식으로는 다른 인스턴스의 캐시를 비울 수 없다.
- `records.words`에는 예외를 적용한 뒤의 결과가 남는다. 예외로 걸러진 검출은 기록에서 빠지므로 ADR 0008의 분석 입력과 관리자 통계의 검출률은 예외 적용 후 기준이 된다. 대신 여러 계정이 같은 표현을 예외로 두었는지를 `whitelists`에서 집계하면 전역 사전에서 제외할 후보를 찾는 새 신호로 쓸 수 있다.
- 새 테이블 하나와 오류 상태 코드 하나가 추가된다.

## Alternatives
- **API Key 단위로 소유하는 방식**: 택하지 않았다. 재발급이 기존 키를 만료시키고 새 행을 만드는 방식이라 재발급 때마다 목록이 끊긴다. 같은 목록을 여러 키에 쓰려면 복제해야 한다.
- **계정당 목록 하나를 자동으로 적용하는 방식**: 택하지 않았다. 한 계정이 성격이 다른 서비스를 운영하면 예외가 섞인다. 요청에 ID를 싣는 방식은 예외 적용 여부가 요청에 드러나므로 결과를 예측하기 쉽다.
- **요청당 그룹 하나만 적용하는 방식**: 택하지 않았다. 공통 예외와 화면별 예외를 나눠 조합할 수 없어 같은 단어를 여러 그룹에 중복 등록해야 한다.
- **구절 안에서만 예외로 두는 방식**: 택하지 않았다. `시발점`을 등록하면 그 구절에서만 예외가 되는 방식으로 더 안전하지만, 구현이 한 단계 어렵고 고객이 쓰기에도 헷갈린다. ADR 0008의 전역 화이트리스트를 구현할 때 함께 검토한다.
- **단어를 별도 테이블로 정규화하는 방식**: 택하지 않았다. 상한이 있는 짧은 목록이라 컬럼 하나로 충분하고, 필터 경로에서 여러 행을 읽지 않아도 된다. 상한을 크게 올려야 하면 그때 분리한다.
- **필터 결과 캐시의 키에 `whitelistIds`를 넣는 방식**: 택하지 않았다. 그룹을 고칠 때마다 무효화가 필요해지고, 최대 1,000건인 캐시가 그룹 조합별로 쪼개져 적중률이 떨어진다.
