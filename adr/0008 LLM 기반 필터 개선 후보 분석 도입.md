# 8. LLM 기반 필터 개선 후보 분석 도입

## Status
제안 (2026.09.10)

## Context
필터 사전을 바꾸는 경로는 관리자의 직접 등록과 단어 요청 승인 두 가지이며, 둘 다 사람이 문제를 먼저 발견해야 시작된다. 잘못 등록된 단어, 실제 요청에 나타난 우회 표현, 정상 구절 안의 오검출은 `records`에 흔적이 남지만 이를 살펴보는 절차가 없다.

기록을 분석 근거로 쓸 때는 다음 제약을 전제로 해야 한다. 현재 `words`는 검출 원문 조각을 `/`로 연결한 문자열이다. 사전 단어와 같다고 단정하지 않는다. QUICK은 첫 검출만 기록하므로 나머지 표현이 없다는 이유만으로 미탐을 확정하지 않는다. 캐시 적중 요청 등이 기록에서 빠지므로 기록 수를 전체 요청 빈도로 해석하지 않는다.

## Decision
관리자가 실행하는 분석 API를 추가한다. 서버는 지정한 날짜의 요청 기록을 LLM에 전달해 단어 제외, 우회 표현 추가, 화이트리스트 추가 후보를 받아 관리자에게 반환한다. 후보는 제안일 뿐이며 사전에 자동으로 반영하지 않는다.

이번에는 후보를 생성해 관리자에게 반환하는 단계까지 구현한다.

### 라이브러리와 호출 방식

- **OpenAI Java SDK (`com.openai:openai-java`)**로 Responses API를 호출한다. SDK는 `profanity-api`에 추가하며 버전은 구현 시 프로젝트 호환성을 확인해 고정한다.
- **Jackson**은 기존 의존성을 재사용하여 프롬프트·스키마 로딩과 응답 변환에 사용한다.
- **Spring MVC / Validation / Data JPA**는 기존 관리자 API, 요청 검증, 기록 조회에 사용한다.

모델은 서버 설정으로 지정한다. 기존 `prompt.json`의 `system`은 모델 지시로, `response.schema.json`은 Structured Outputs의 `text.format`에 `type=json_schema`, `name=filter_improvement`, `strict=true`와 함께 전달한다. 도메인은 SDK 타입에 의존하지 않는다.

Java SDK는 모델 API를 직접 호출하는 방식이다. Codex SDK나 별도 Node 실행 환경은 사용하지 않는다. [공식 Java SDK 안내](https://developers.openai.com/api/docs/libraries), [Structured Outputs 안내](https://developers.openai.com/api/docs/guides/structured-outputs)

### 관리자 API 계약

`POST /api/v1/admin/filter-improvements/analyze`

로그인 JWT와 ADMIN 역할을 요구한다. 기존 관리자 API처럼 `@Hidden`과 `ApiResponse<T>`를 사용한다. 초기에는 제한된 건수를 동기 분석하고 결과를 반환한다.

요청:

```json
{
  "date": "2026-09-09",
  "maxRecords": 100,
  "maxCandidates": 10
}
```

| 요청 값 | 의미 | 초기 제안 |
|---|---|---|
| `date` | 분석할 날짜 | 필수, Asia/Seoul 기준 |
| `maxRecords` | 이번 요청에서 분석할 최대 기록 수 | 기본 100, 1~500 |
| `maxCandidates` | 반환할 최대 후보 수 | 기본 10, 1~50 |

해당 날짜의 `[00:00, 다음 날 00:00)`을 조회하고 `created_at, id` 오름차순으로 최대 건수만 분석한다. 초기에 전체 하루 분석을 보장하지 않으며, 나머지 기록이 있으면 `hasMore=true`로 알린다. `records.created_at`은 Asia/Seoul의 벽시계로 저장된다(2026.09.21 운영 DB에서 확인). 조회 경계는 `AdminStatisticsService`와 같은 방식으로 만들어 저장 시각과 같은 기준을 갖게 한다.

응답은 기존 `ApiResponse`로 감싸며, 아래 예시는 `data` 부분이다. 후보 필드는 관리자 API에서 camelCase로 제공한다.

```json
{
  "date": "2026-09-09",
  "analyzedCount": 100,
  "hasMore": true,
  "candidates": [
    {
      "type": "ADD_WHITELIST",
      "target": "시발",
      "context": "시발점",
      "recordIds": [101],
      "reason": "출발점을 뜻하는 정상 표현에 검출 단어가 포함되어 있다.",
      "confidence": 95
    }
  ]
}
```

`analyzedCount`는 실제 분석한 기록 수다. 정상적으로 분석했지만 후보가 없으면 `candidates=[]`를 반환한다. 모델 호출 실패, 거절, 불완전 응답, 스키마 불일치는 오류로 처리하며 빈 후보로 숨기지 않는다.

### LLM에 전달할 값

프롬프트와 응답 스키마를 별도로 전달하고, 분석 데이터에는 아래 값만 넣는다. 예시는 합성 데이터다.

```json
{
  "max_candidates": 10,
  "records": [
    {
      "id": 101,
      "text": "시발점에서 출발합니다",
      "mode": "FILTER",
      "words": "시발"
    }
  ],
  "dictionary_terms": ["시발"]
}
```

`id`는 근거 연결용 기록 ID, `text`는 요청문, `mode`는 QUICK/NORMAL/FILTER, `words`는 기존 검출 문자열이다. `dictionary_terms`에는 관련 사전 단어를 서버에서 조회해 넣으며 확인하지 못하면 null을 전달한다.

### LLM에서 받을 값

기존 `response.schema.json`을 그대로 사용한다. 최상위는 `candidates` 배열이며 각 후보는 다음 필드를 모두 반환한다.

| 응답 값 | 의미 |
|---|---|
| `type` | `REMOVE_TERM`, `ADD_EVASION`, `ADD_WHITELIST` 중 하나다. |
| `target` | 제외할 사전 단어, 추가할 실제 우회 표현 또는 예외 처리할 검출 표현이다. |
| `context` | 화이트리스트에 필요한 최소 원문 구절이다. 다른 유형은 null이다. |
| `record_ids` | 후보를 뒷받침하는 입력 기록 ID 목록이다. |
| `reason` | 판단 근거 한 문장이다. |
| `confidence` | 0~100 정수이며 모델이 판단한 확신 정도다. 자동 승인 확률이 아니다. |

- **REMOVE_TERM**은 단어 자체가 잘못 등록된 경우다. 특정 문장에서 정상이라는 이유만으로 단어 전체를 제외하지 않는다.
- **ADD_EVASION**은 실제 요청문에서 발견한 우회 욕설이다. 새로운 표현을 임의로 생성하지 않는다.
- **ADD_WHITELIST**는 정상 구절 안의 특정 검출만 예외로 둔다. 예를 들어 `시발점` 안의 `시발`을 예외로 제안하되 같은 문장의 다른 욕설까지 허용하지 않는다.

서버는 스키마와 근거를 확인하고 같은 유형·표현·문맥의 중복을 정리한 뒤 점수 내림차순으로 반환한다. 근거 없는 후보는 정상 결과로 채택하지 않는다.

## Consequences
- 사람이 찾아내야 했던 오검출과 미검출 후보를 기록에 근거해 제안받는다. 후보마다 근거가 된 기록 ID가 붙으므로 관리자가 판단 근거를 바로 확인할 수 있다.
- 요청 텍스트가 외부 모델 API로 전송된다. 요청 텍스트에는 이용자가 입력한 문장이 그대로 담기며, 전화번호 형태의 문자열이 포함된 기록도 실제로 있다(2026.09.21 집계 기준 약 1천 건). 개인정보 처리방침의 외부 제공 관련 항목에 반영이 필요한지 도입 전에 확인해야 한다.
- `profanity-api`에 `com.openai:openai-java` 의존성이 추가되고 분석을 실행할 때마다 모델 호출 비용이 발생한다.
- 모델 호출 실패, 거절, 불완전 응답, 스키마 불일치를 빈 후보로 숨기지 않으므로 관리자 화면이 분석 오류를 직접 다뤄야 한다.
- 새 테이블, 후보 저장, 일일 스케줄, 사전 자동 변경, 화이트리스트 실제 적용은 후속 범위로 남는다. 자동 반영 점수 기준은 아직 정하지 않았다.

## Alternatives
- **Codex SDK나 별도 Node 실행 환경을 두는 방식**: 택하지 않았다. 현재 Java 서버에서 모델 API를 직접 호출한다.
- **후보를 사전에 자동으로 반영하는 방식**: 택하지 않았다. `confidence`는 모델이 판단한 확신 정도일 뿐 자동 승인 확률이 아니며, 자동 반영 점수 기준도 정해지지 않았다.
