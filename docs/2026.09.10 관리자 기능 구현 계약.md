# 관리자 기능 구현 계약

## 범위와 경계

승인된 다섯 메뉴를 실제 저장소/API에 연결한다. 역할은 CLIENT, ADMIN 두 종류이며 기존 사용자와 신규 가입자는 CLIENT가 기본이다. 실제 관리자 지정, 운영 DB 접속·마이그레이션 실행, 배포 및 Git 쓰기는 수행하지 않는다. 기존 UI 목업은 개발 모드의 명시적인 preview 쿼리에서만 사용할 수 있게 분리한다.

신규 마이그레이션은 코디네이터가 V5__admin_portal.sql 하나만 작성한다. 기존 V1~V4 및 보관된 백엔드 패치는 수정·적용하지 않는다. MySQL 임시 테스트 컨테이너에서 V4 데이터 삽입 → V5 전환 전후를 검증한다. 과거 시각과 작업자는 알 수 없으면 NULL로 둔다.

## API 공통 계약

신규 컨트롤러는 @Hidden을 직접 적용한다. ApiResponse 데이터 래핑과 기존 오류 처리 패턴을 사용한다. 목록은 {items, page, hasNext}, page는 0부터 시작하고 기본 size=20, 최대 100이다. query는 검색 문자열이며 빈 문자열은 전체이다. 데이터가 없으면 빈 목록을 반환한다. API Key 해시나 원문을 반환하지 않는다.

/api/v1/admin/**는 AUTH_LOGIN_JWT 및 ROLE_ADMIN을 함께 요구한다. 사용자 상태와 역할은 인증 시 DB를 기준으로 확인한다. API Key의 WRITE 권한은 관리자 접근 권한이 아니다. /api/v1/news GET은 인증 없이 공개된 소식만 조회한다. /api/v1/dashboard/inquiries는 로그인한 CLIENT와 ADMIN 모두 본인의 문의만 처리한다.

## 역할별 파일 소유권

- 인증·운영 워커: 사용자 역할/상태/로그인 시각, SecurityConfig 및 인증 경로, 필터 사전, API Key 관리자 기능, 감사 기록, 관련 저장소/테스트. 기존 AuthController 응답에 role 및 admin을 추가한다.
- 콘텐츠 워커: 소식, 문의/답변, 기존 단어 요청의 문의 연결 및 승인, 관련 저장소/테스트. SecurityConfig, UI, SQL 마이그레이션은 수정하지 않는다.
- UI 워커: ui/app/src 안의 관리자·소식·인증 UI/API 연동. 백엔드·SQL 수정 금지.
- 코디네이터: 단일 SQL 마이그레이션, 전후 MySQL 테스트, 계약 통합 및 최종 검증.

공유 변경이 필요하면 코디네이터에게 먼저 알린다. 전체 Spotless 및 Gradle 빌드·테스트는 코디네이터가 실행하여 동시 빌드를 피한다. 워커는 담당 테스트를 작성하고 컴파일 검증 요청을 보낸다.

## 소식 계약

GET /api/v1/news?category=&query=&page=0&size=20 및 GET /api/v1/news/{id}.
GET /api/v1/admin/news?status=&category=&query=&page=0&size=20, POST /api/v1/admin/news, PUT /api/v1/admin/news/{id}, DELETE /api/v1/admin/news/{id}.
쓰기: {title, category, content, status}. status=DRAFT|PUBLISHED. category=NOTICE|CHANGELOG|MAINTENANCE|ISSUE.
항목: {id, title, category, content, status, createdAt, updatedAt, publishedAt}. 공개 목록은 본문 생략 가능. 비공개 상세는 외부에서 404. 게시 후 임시 저장 선택은 비공개 전환으로 처리하며 UI에서 명확히 안내한다.
news_posts: id BIGINT AUTO_INCREMENT, title VARCHAR(160), category VARCHAR(30), content_markdown MEDIUMTEXT, status VARCHAR(30), created_by/updated_by BINARY(16), created_at/updated_at DATETIME(6), published_at DATETIME(6) NULL.

## 문의 계약

GET /api/v1/admin/inquiries?type=&status=&query=&page=0&size=20, GET /api/v1/admin/inquiries/{id}, PATCH /api/v1/admin/inquiries/{id}/status {status}, POST /api/v1/admin/inquiries/{id}/replies {content, resolve}.
로그인 사용자: GET/POST /api/v1/dashboard/inquiries 및 GET /api/v1/dashboard/inquiries/{id}. 신규 문의 {type,title,content,word?,requestType?,severity?}. 단어 요청의 requestType은 기존 외부 API ADD|REMOVE|MODIFY 의미를 보존한다.
문의 항목: {id,type,title,content,status,requesterName,requesterEmail,createdAt,updatedAt,resolvedAt}; 상세에는 replies:[{id,content,authorName,createdAt}]와 wordRequest:{id,word,reason,severity,requestType,status}|null.
GET 목록과 공개 API 계약은 고객용 OpenAPI 노출 여부를 바꾸지 않는다. 기존 외부 /word/request는 유지하면서 같은 트랜잭션으로 문의를 생성한다.
POST /api/v1/admin/inquiries/{id}/word-decision {decision: APPROVE|REJECT, reason}. 단어 승인만 사전을 변경하며 일반 답변 완료는 사전 변경과 분리한다. 승인 중복 적용을 막는다. MODIFY에 변경 대상 표현이 없는 기존 계약은 임의 추정해 변경하지 말고 명시적 오류로 처리한다.

inquiries: id BIGINT AUTO_INCREMENT, type VARCHAR(30), title VARCHAR(160), content TEXT, requester_user_id BINARY(16) NULL, requester_api_key_id BINARY(16) NULL, status VARCHAR(30), assigned_to BINARY(16) NULL, created_at/updated_at DATETIME(6), resolved_at DATETIME(6) NULL.
inquiry_replies: id BIGINT AUTO_INCREMENT, inquiry_id BIGINT, author_user_id BINARY(16), content TEXT, created_at DATETIME(6).
word_management: inquiry_id BIGINT NULL UNIQUE 추가. request_user_id는 NULL 허용으로 완화하여 로그인 사용자 문의는 API Key ID를 요구하지 않는다. 기존 request_user_id는 실제 API Key ID이므로 보존하며 users로 직접 연결하지 않는다. 마이그레이션에서 기존 행마다 문의를 만들고 api_keys와 LEFT JOIN하여 확인 가능한 요청자만 연결한다. 기존 단어 요청 필드를 삭제하지 않는다.

## 운영 계약

GET /api/v1/admin/words?query=&isUsed=&page=0&size=20, POST /api/v1/admin/words {word}, PUT /api/v1/admin/words/{id} {word,isUsed}. isUsed=Y|N.
항목 {id,word,isUsed,source,createdAt,updatedAt}. source=BASE|ADMIN|REQUEST|UNKNOWN. 과거 출처는 UNKNOWN.
GET /api/v1/admin/users?query=&role=&page=0&size=20, PATCH /api/v1/admin/users/{id}/status {status:ACTIVE|DISABLED}.
항목 {id,displayName,primaryEmail,role,status,lastLoginAt,createdAt}. 자기 계정 및 ADMIN 계정 비활성화는 이번 기능에서 금지한다. 관리자 역할 변경 API는 만들지 않는다.
GET /api/v1/admin/keys?query=&status=&page=0&size=20, POST /api/v1/admin/keys/{id}/revoke {reason}.
항목 {id,name,keyHint,ownerName,email,active,issuedAt,expiredAt,lastUsedAt}. status=ACTIVE|EXPIRED.

users: role VARCHAR(30) NOT NULL DEFAULT CLIENT, last_login_at DATETIME(6) NULL.
profanity_word: source VARCHAR(30) NOT NULL DEFAULT UNKNOWN, created_at/updated_at DATETIME(6) NULL, created_by/updated_by BINARY(16) NULL.
api_keys: last_used_at DATETIME(6) NULL, revoked_by BINARY(16) NULL, revocation_reason VARCHAR(500) NULL.
admin_audit_logs: id BIGINT AUTO_INCREMENT, actor_user_id BINARY(16), action VARCHAR(60), target_type VARCHAR(60), target_id VARCHAR(100), reason VARCHAR(500) NULL, created_at DATETIME(6).
인증·운영 워커가 app.application.admin.AdminAuditService.record(UUID actorId,String action,String targetType,String targetId,String reason,Instant now)를 제공한다. 감사 기록에 요청 원문, 응답, 인증정보를 넣지 않는다. 업무 변경과 같은 트랜잭션으로 기록한다.

## 주요 위험과 검증

기존 문의 ID 관계 오인, 비공개 소식 유출, CLIENT/API Key의 관리자 접근, 사전 수정 후 Trie 미반영, 기존 JWT 호환성, 중복 승인 및 데이터 손실을 회귀 검증한다. 기존 데이터의 상태와 키 소유권을 보존하고 모든 계정을 CLIENT로 초기화한다. 실제 관리자 지정은 승인된 후속 작업이다.

## 구현 중 확정 사항

- PageView<T>는 콘텐츠 워커가 shared에 정의한다. StatusCode.java는 코디네이터가 편집하며 인증·운영 4060~4079, 콘텐츠 4080~4099를 배정한다.
- 사전 동기화는 Y인 단어만 적재하고 각 인스턴스에서 매 60초 다시 동기화한다. 관리자 변경은 커밋 이후 반영하고 결과 캐시도 비운다.
- 최근 키 사용 시각은 60초 단위 조건부 갱신으로 기록한다. 시각 미상은 NULL이다.
- 사용자 삭제는 제공하지 않으며 감사/작성자 FK는 RESTRICT로 유지한다. 테스트 초기화는 신규 테이블도 포함한다.

- 문의 type=GENERAL|WORD_REQUEST, status=RECEIVED|IN_PROGRESS|RESOLVED. 단어 처리 상태=REQUEST|APPROVED|REJECTED.
- 신규 소식과 문의 시간은 Instant/UTC다. 과거 단어 요청 requested_at은 Asia/Seoul LocalDateTime이므로 백필 시 신규 문의 시간만 9시간을 빼고 원본은 보존한다.
