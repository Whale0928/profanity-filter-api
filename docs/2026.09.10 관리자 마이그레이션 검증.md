# 관리자 마이그레이션 검증

## 변경 범위

신규 파일은 `profanity-storage/rdb/src/main/resources/db/migration/V5__admin_portal.sql` 하나다. V1~V4는 수정하지 않는다. 기존 보관용 패치는 적용하지 않는다. 실제 운영 DB와 공유 개발 DB에는 접근하거나 실행하지 않았다.

V5는 사용자 역할/로그인 시각, 사전 출처/작업자/시각, 키 사용 및 만료 메타데이터를 추가하고 소식·문의·답변·감사 테이블을 만든다. 기존 사용자는 모두 CLIENT다. 특정 계정을 ADMIN으로 바꾸는 SQL이나 기본 관리자 계정은 없다.

기존 `word_management.request_user_id` 값은 API Key ID다. 이를 users.id로 해석하지 않고 api_keys와 연결하여 확인 가능한 소유자만 문의에 기록한다. API Key가 없거나 소유자가 미정인 과거 요청도 삭제하지 않는다. 기존 ID, 단어, 사유, 심각도, 요청 유형, 상태, 요청 시각은 그대로 보존한다. 원본 requested_at은 Asia/Seoul 시각이므로 신규 문의의 UTC 시각으로 복사할 때만 9시간을 빼며 원본 칼럼은 수정하지 않는다. 기존 요청은 자동 승인하지 않으며 문의에서 다시 검토할 수 있는 RECEIVED로 둔다. 제목만 최대 160자로 요약하며 원본 단어와 사유는 보존한다.

로그인 사용자 문의는 API Key가 없어도 접수할 수 있으므로 request_user_id는 NULL을 허용한다. 과거 사전의 출처는 UNKNOWN이며, 기록하지 않았던 등록자/수정자/시각/키 최근 사용 시각은 NULL이다. 과거 값인 것처럼 마이그레이션 시각을 넣지 않는다.

## 로컬 전후 검증

`AdminPortalMigrationTest`는 일회용 MySQL 8.4 Testcontainers에서 두 경로를 검증한다.

1. 빈 DB에 V1부터 V5 적용 → 5개 적용 → 재실행 0개 → Flyway validate 성공.
2. V4에 활성/만료 키, 소유자 없는 키, 비활성 사용자, 사용 중지 단어, 소유자 관계가 끊긴 단어 요청을 삽입 → 원본 값을 읽어 보관 → V5 한 개만 적용 → 원본 값과 비교.

두 번째 경로에서는 요청자의 API Key ID가 사용자 ID와 우연히 같은 경우도 삽입하여 잘못된 사용자 연결이 생기지 않는지 확인한다. 200자 한글 표현의 원본 보존과 목록 제목 길이, 백필 후 AUTO_INCREMENT, 신규 역할 기본값 CLIENT, USER 역할 거부, 문의 FK 무결성 및 재실행 무변경을 검증한다.

실행 명령: `./gradlew --no-daemon :profanity-api:unitTest --tests app.migration.AdminPortalMigrationTest`
최종 결과: 시간대 변환을 포함한 2개 통과, 실패 0개. V1~V4의 SHA-256은 작업 전 기준과 모두 일치했다.

통합 검증 명령은 `./gradlew --no-daemon spotlessApply staticCheck unitTest apiE2eTest supportTest`이며 통과했다. 단위·슬라이스 292개, API E2E 70개, 테스트 지원 5개에서 실패와 건너뛴 테스트가 없었다. 관리자 E2E는 CLIENT/API Key 접근 차단, 기존 JWT에 대한 역할 회수, 소식 공개·비공개 전환, 문의 소유권과 답변, 단어 승인 중복 방지, 키 만료 및 사전 수정 후 캐시 갱신을 포함한다. 추가로 같은 단어 요청의 동시 승인 시 사전과 감사 기록이 한 번만 저장되는지, DB 연결 하나로 인증과 최근 사용 기록이 가능한지를 검증했다. 사용 기록 경로의 중첩 트랜잭션으로 발생한 연결 대기 실패를 재현한 뒤 조회와 기록의 연결 점유를 분리하여 동일 테스트가 통과했다. 고객용 OpenAPI는 기존 외부 연산 5개를 유지한다. 수동 동기화 경로도 이전 필터 결과 캐시를 비우는지 E2E로 확인했다.

UI는 `npm run build`, `npm run verify:discovery`가 통과했고 공개 탐색 산출물 5개를 확인했다. localhost 브라우저에서는 명시적 개발 미리보기의 관리자 레이아웃과 문의 메뉴, 일반 회원의 관리자 메뉴 숨김 및 직접 접근 차단을 확인했다. 이후 로컬 Docker MySQL을 백업한 뒤 실행 중이던 백엔드를 재기동하여 V5 한 개를 적용했다. 기존 사용자 1개와 키·단어·단어 요청 각 0개가 유지되었고 Flyway V1~V5 성공을 확인했다. Brave에서 GitHub와 Google의 실제 로그인 및 새로고침 후 세션 유지를 확인했다. 사용자 승인에 따라 지정된 로컬 계정 한 개의 역할을 CLIENT에서 ADMIN으로 별도 변경했다. 운영 DB에는 적용하지 않았다.

## 향후 운영 적용 전 확인

운영 적용은 별도 승인 후 수행한다. MySQL DDL은 단일 파일이어도 전체가 하나의 원자적 트랜잭션으로 롤백되는 것으로 간주하면 안 된다.

- 적용 중 기존 단어 요청이 계속 들어오면 백필 시점과 연결 갱신 시점이 어긋날 수 있으므로 쓰기 중단 구간을 확보한다. 이전 서버가 새 요청을 기록하는 상태에서 마이그레이션을 끝내지 않는다.
- Flyway 이력이 V4이고 실패한 이력이 없는지, 실제 스키마가 저장소 V4와 일치하는지 확인한다. `news_posts` 등 동일 이름의 별도 운영 테이블 존재 여부도 확인한다.
- users/api_keys/profanity_word/word_management의 건수와 상태 분포, 소유권 없는 요청 수를 읽기 전용으로 확인한다. 요청 원문과 키를 로그에 출력하지 않는다.
- 검증된 백업 및 복원 절차를 확보하고 운영과 같은 MySQL 버전의 복제본에 먼저 적용한다. 기존 버전과 신규 버전의 혼합 운영은 허용하지 않는다.
- 실패 시 Flyway repair 또는 SQL 재실행으로 무작정 진행하지 않는다. DDL 반영 지점과 백필 상태를 먼저 확인하고, 검증된 백업 복원 또는 검토한 복구 절차를 따른다.

## 적용 후 확인할 항목

원본 요청 건수와 기존 필드 값 보존, 모든 기존 요청의 inquiry_id 연결, API Key 기반 소유권 대응, CLIENT 초기화, 과거 미상 값 NULL 유지, Flyway V5 성공 및 validate를 확인한다. 그 후 승인된 대상에 한해 별도로 관리자 역할을 지정하고 접근 제어를 점검한다.

사용 중지 단어 제외 및 사전 갱신 전파는 기존 동작을 바로잡는 변경이다. 운영 사전의 Y/N 분포를 사전에 확인하고 변경 후 검출 결과를 확인해야 한다. 이번 로컬 검증은 운영 데이터 검증이나 운영 배포 완료를 의미하지 않는다.

## 독립 Opus 검토 후 보완

Orca orchestration으로 인증·운영(Opus), 소식·문의(Opus), UI(Sonnet)를 분담하고 별도의 Opus가 구현을 읽기 전용으로 검토했다. 검토 후 다음 사항을 반영했다.

- 수동 사전 동기화에서도 변경 이벤트를 발행하여 결과 캐시가 남지 않도록 했다. 해당 경로의 비밀번호 평문 로그도 제거했다.
- 최근 사용 기록의 DB 및 트랜잭션 실패는 경고만 남기고 이미 검증된 API Key 인증은 유지한다. 프로그래밍 오류는 숨기지 않는다. 두 동작을 단위 테스트로 검증했다.
- 실제 호출되지 않던 승인 전용 사전 메서드와 그 전용 테스트 4개를 제거했다. 승인 검증은 실제 AdminInquiryService의 기존 테스트와 E2E에서 수행한다.
- 같은 단어의 동시 등록으로 MySQL 고유 제약이 충돌하면 HTTP 409와 WORD_ALREADY_EXISTS를 반환한다. 해당 제약만 인식하고 다른 제약을 오인하지 않는지 단위 테스트로 검증했다. 서로 다른 문의 두 건의 실제 DB 경합을 강제로 재현하는 검증은 수행하지 않았다.
