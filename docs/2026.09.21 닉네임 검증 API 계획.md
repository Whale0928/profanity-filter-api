# 닉네임 검증 API 계획

가입과 프로필 변경 단계에서 닉네임을 쓸 수 있는지 한 번에 판정하는 API를 추가한다. 이 문서는 구현할 계약이며 아직 구현된 API가 아니다.

## 배경

운영 DB의 `records`를 집계해 보면 이 API는 이미 닉네임 검사 용도로 쓰이고 있다. 아래는 2026.09.21 기준 누적 341,951건을 모드별로 나눈 값이다.

| 모드 | 요청 수 | 비중 | 평균 입력 길이 | 검출률 |
|---|---|---|---|---|
| FILTER | 339,696 | 99.4% | 11.3자 | 1.44% |
| NORMAL | 2,082 | 0.6% | 81.3자 | 26.37% |
| QUICK | 202 | 0.1% | 13.6자 | 10.89% |

입력 길이 분포도 같은 방향을 가리킨다. 20자 이하가 302,073건으로 전체의 88%를 차지하고, 100자를 넘는 요청은 2,028건뿐이다. 문장을 검사하는 호출이 아니라 한 줄짜리 짧은 문자열을 마스킹하는 호출이 사실상 전부다.

그런데 현재 API는 비속어만 판정한다. 서비스가 닉네임을 거부해야 하는 사유는 비속어 외에도 여럿이므로, 이용하는 쪽에서 나머지 규칙을 각자 구현하고 있을 것으로 보인다. 이미 형성된 사용 방식을 정식 기능으로 끌어올리는 것이 이 계획의 목적이다.

## 판정 항목

비속어 판정은 기존 사전과 Trie를 그대로 사용한다. 여기에 다음 규칙을 더한다.

사칭 표현은 `관리자`, `운영자`, `admin`, `official`처럼 운영 주체를 사칭하는 표현이다. 커뮤니티에서 실제 피해로 이어지는 유형이라 비속어와 별개로 다룬다.

자모 전용 문자열은 `ㅋㅋㅋ`이나 `ㅇㅇ`처럼 완성형 글자 없이 자모만으로 이루어진 입력이다. 특수문자 규칙은 허용할 문자 집합과 연속 사용 횟수를 제한한다. 길이 규칙과 공백 규칙은 최소와 최대 길이, 앞뒤 공백과 연속 공백을 다룬다.

사칭 표현 목록은 성격이 비속어와 다르다. 별도 테이블을 만들기보다 `profanity_word`의 `WordSource`를 확장해 같은 테이블에서 관리하는 방안을 먼저 검토한다. 사전이 하나로 유지되면 동기화 경로와 관리자 화면을 그대로 쓸 수 있다.

## API 계약

`POST /api/v1/nickname/verify`

인증은 기존 외부 API와 같이 `X-API-KEY`를 사용한다. 응답은 기존 규약대로 HTTP 200에 `status.code`로 비즈니스 결과를 전달한다.

요청은 다음과 같다.

```json
{ "nickname": "관리자김철수" }
```

응답의 `data` 부분은 다음 형태를 따른다.

```json
{
  "nickname": "관리자김철수",
  "allowed": false,
  "reasons": [
    { "code": "IMPERSONATION", "detail": "관리자" }
  ]
}
```

거부 사유는 코드로 내려 이용하는 쪽이 안내 문구를 직접 정하게 한다. 사유가 여럿이면 모두 담아 한 번에 고칠 수 있게 한다. 사유 코드는 비속어, 사칭 표현, 자모 전용, 허용하지 않는 문자, 길이 위반, 공백 위반을 구분한다.

## 폴더 구조

```text
profanity-domain/src/main/java/app/
├── application/nickname/
│   ├── NicknameVerificationService.java   # 판정 조립
│   ├── NicknameRule.java                  # 개별 규칙 인터페이스
│   └── NicknameVerdict.java               # 판정 결과와 사유 목록
└── domain/nickname/
    └── NicknameRejectionReason.java       # 사유 코드

profanity-api/src/main/java/app/
├── presentation/
│   └── NicknameController.java
└── dto/request/
    └── NicknameVerifyRequest.java
```

비속어 판정은 기존 `ProfanityFilter`를 주입해 재사용하고, 나머지 규칙만 새로 쓴다. 규칙을 인터페이스로 나누면 항목을 추가할 때 서비스를 건드리지 않아도 된다.

## 먼저 정해야 할 것

규칙 임계값을 설정으로 뺄지 상수로 둘지 정해야 한다. 길이와 허용 문자는 서비스마다 다를 수 있는데, API Key별 설정으로 가면 저장소와 관리 화면까지 범위가 커진다. 우선은 고정 규칙으로 시작하고 요구가 확인되면 그때 확장하는 편이 낫다.

판정 요청을 `records`에 남길지도 정해야 한다. 남긴다면 `mode` 값을 어떻게 구분할지 함께 정한다. 기존 통계가 모드별로 집계하고 있어 새 값이 들어오면 화면에 그대로 드러난다.
