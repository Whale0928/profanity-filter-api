# 개인정보 검출 계획

사용자가 입력한 문장에서 전화번호나 계좌번호 같은 개인정보를 찾아 알려 주고 마스킹하는 기능을 추가한다. 이 문서는 구현할 계약이며 아직 구현된 API가 아니다.

## 배경

비속어 필터를 쓰는 서비스는 같은 입력 지점에서 개인정보 노출 문제를 함께 겪는다. 채팅과 게시글에 전화번호와 계좌번호가 그대로 올라가는 상황이다.

두 기능은 도입 동기의 무게가 다르다. 비속어 차단은 서비스가 스스로 정하는 품질 문제이지만, 개인정보 노출은 개인정보보호법이 요구하는 관리 의무와 맞닿아 있다. 이미 비속어 검사를 붙여 둔 곳이라면 같은 호출 지점에 검사 하나를 더하는 비용이 낮다.

구현 관점에서도 기존 구조를 크게 벗어나지 않는다. 입력을 받아 검출 목록과 마스킹 결과를 돌려주는 흐름은 지금 필터와 같고, 매칭 방식만 Aho-Corasick 대신 정규식을 쓴다.

## 검출 대상

휴대전화번호와 유선전화번호, 주민등록번호, 계좌번호, 카드번호, 이메일 주소를 대상으로 한다.

주민등록번호와 카드번호는 형식만 맞추면 오탐이 많다. 주민등록번호는 마지막 자리 검증식이 있고 카드번호는 Luhn 검사가 있으므로, 형식 일치 뒤에 검증식을 한 번 더 적용해 정확도를 올린다. 계좌번호는 은행마다 자릿수가 달라 단순 숫자 나열과 구분하기 어렵다. 앞뒤 문맥에 은행명이나 `계좌`, `입금` 같은 단어가 있을 때만 검출하는 방식을 검토한다.

주소는 이번 범위에서 제외한다. 한국 주소는 형태가 다양해 정규식만으로는 오탐이 감당되지 않는다.

## API 계약

`POST /api/v1/privacy/inspect`

인증은 기존 외부 API와 같이 `X-API-KEY`를 사용하고, 응답은 HTTP 200에 `status.code`로 결과를 전달한다.

요청은 다음과 같다.

```json
{ "text": "연락처는 010-1234-5678 입니다", "mask": true }
```

응답의 `data` 부분은 다음 형태를 따른다.

```json
{
  "detected": [
    { "type": "PHONE", "start": 6, "length": 13 }
  ],
  "masked": "연락처는 ************* 입니다"
}
```

검출 값 자체는 응답에 담지 않는다. 담으면 로그와 중계 구간에 개인정보가 그대로 흐른다. 위치와 길이만 내려 주고 원문은 이용하는 쪽이 이미 갖고 있는 값을 쓰게 한다.

## 기록 정책을 먼저 정해야 한다

이 기능에서 가장 중요한 결정은 검출 규칙이 아니라 요청 기록이다.

현재 `TrackingRecorder`는 요청 원문을 `records.request_text`에 그대로 저장한다. 컬럼은 `varchar(255)`이고 보관 기간에 대한 정책도 따로 없다. 개인정보 검출 API를 열면 개인정보가 담긴 문장이 그 컬럼에 쌓인다. 개인정보 노출을 막아 주는 기능이 개인정보를 모으는 결과가 되므로 반드시 먼저 정리해야 한다.

세 가지 방안을 검토한다. 첫째는 이 엔드포인트만 원문을 저장하지 않고 검출 유형과 건수만 남기는 방법이다. 둘째는 저장 전에 마스킹한 문자열을 저장하는 방법이다. 셋째는 기록 자체를 남기지 않는 방법이다.

둘째 방안이 통계와 개선 작업에 쓸 자료를 남기면서 위험을 줄이므로 우선 검토한다. 다만 마스킹 실패분이 그대로 저장되는 위험이 남으므로, 검출 규칙이 안정될 때까지는 첫째 방안으로 시작하는 편이 안전하다.

기존 필터 API의 `request_text` 저장 정책도 이 기회에 함께 점검한다. 지금도 사용자가 문장을 그대로 보내면 개인정보가 들어올 수 있다.

## 폴더 구조

```text
profanity-domain/src/main/java/app/
├── application/privacy/
│   ├── PrivacyInspectionService.java    # 검출 조립과 마스킹
│   └── PrivacyPattern.java              # 유형별 정규식과 검증식
└── domain/privacy/
    ├── PrivacyType.java                 # 검출 유형
    └── PrivacyMatch.java                # 검출 위치와 길이

profanity-api/src/main/java/app/
├── presentation/
│   └── PrivacyController.java
└── dto/request/
    └── PrivacyInspectRequest.java
```

## 위험과 고려 사항

정규식은 입력 길이에 따라 성능이 급격히 나빠질 수 있다. 역추적이 심한 패턴을 쓰지 않도록 작성하고, 입력 길이 상한을 둔다.

오탐이 나면 정상 입력이 마스킹되어 사용자 경험을 해친다. 검출 유형별로 켜고 끌 수 있게 해서 이용하는 쪽이 감도를 조절할 수 있게 한다.

검출 규칙을 담은 테스트는 실제 개인정보가 아니라 형식만 같은 가짜 값으로 작성한다. 주민등록번호와 카드번호는 검증식을 통과하는 가짜 값을 만들어 쓴다.

## 이번 범위

첫 구현에서는 휴대전화번호, 이메일, 주민등록번호, 카드번호까지 검출한다. 계좌번호는 문맥 판정이 필요해 다음 단계로 미루고, 주소는 범위에서 제외한다. 기록 정책은 원문을 저장하지 않는 방식으로 시작한다.
